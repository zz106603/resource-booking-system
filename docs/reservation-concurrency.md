# 예약 배타 제약 전환

## 범위와 보존

현재 feat/reservation-api의 공간·예약 API, V1~V3, 입력 검증·취소 이력을 보존하며 중복 방지 경로를 전환한다. 기존 작업 파일은 저장소 외부에 백업했다. AC10은 사용자 확인에 따라 미구현·미검증으로 남긴다. 고부하 벤치마크, 커밋·push는 범위에서 제외한다.

## 결정과 구현 순서

1. 직접 SQL 중복 차단 및 공간 잠금 독립성 테스트로 기존 구현의 실패를 확인한다.
2. V4에 CONFIRMED 한정 공간+tstzrange `[)` 배타 제약을 추가한다. 기존 활성 중복은 자동 수정하지 않고 마이그레이션을 실패시킨다. 설치 역할은 btree_gist를 public에 설치할 권한이 필요하다.
3. 생성은 공간 존재 확인 → 시간 검증 → 명명된 제약을 지정한 INSERT ON CONFLICT DO NOTHING RETURNING → 현재 시각 재검증 → 결과 반환·커밋으로 구성한다. 공간 행 쓰기 잠금과 사전 중복 조회는 사용하지 않는다. DB 제약이 최종 보장이다. 반환 행이 없으면 중복 409다.
4. 취소는 예약 ID 행을 잠근 뒤 상태와 Clock을 확인한다. 같은 공간의 무관한 예약은 잠그지 않는다. 이미 취소된 예약은 최초 취소 시각을 유지한다.
5. 외부 서비스가 재시도를 조율하고 별도 Spring 빈이 REQUIRES_NEW·READ COMMITTED 트랜잭션을 실행한다. self-invocation과 실패한 트랜잭션 내부 재시도를 피한다. 커밋/롤백을 마친 예외만 외부에서 분류한다.
6. 별도로 예외가 발생하면 해당 명명된 제약의 23P01만 중복 409로 변환한다. 일반 생성 충돌은 DO NOTHING의 빈 RETURNING 결과로 판정한다. 40P01만 최초 포함 최대 3회, 각 재시도 전 10~30ms jitter로 재시도한다. 각 시도는 별도 15초 제한이며 전체 HTTP 요청의 전역 제한을 의미하지 않는다. 소진·인터럽트는 503이다. 다른 SQLSTATE는 재시도하지 않는다.
7. 순수 오류 분류·재시도 테스트와 실제 PostgreSQL 교착·롤백·새 트랜잭션, 제약 대기, 취소 경합, 업그레이드 테스트를 실행한다. 마지막에 전체 clean build와 문서 일관성을 확인한다.

## 판단 근거와 한계

- PostgreSQL이 고정되어 있고 활성 시간 구간 무결성이 핵심이므로 부분 배타 제약을 채택한다. 이전 실험의 높은 충돌률에서 교착이 관찰되어, 배타 제약을 추가하는 것만으로 전환 완료로 판단하지 않는다.
- 무잠금 사전 조회는 고충돌 시 빠른 거부에 도움이 될 수 있지만, 진행 중인 취소를 기다리지 않고 먼저 거부하는 의미 차이가 있다. 이번에는 제약의 대기·커밋 결과에 따르며 성능 최적화는 추가하지 않는다.
- 단순 INSERT와 제한 재시도로 전환한 중간 구현에서 기존 8동시 테스트가 201 한 건·503 일곱 건으로 실패했다. 40P01을 반복 재생성하는 경로를 횟수 증가로 감추지 않고, PostgreSQL의 speculative insertion 복구 경로를 쓰는 ON CONFLICT DO NOTHING으로 바꿨다. DO UPDATE는 사용하지 않으며 이름을 지정해 다른 제약 오류를 삼키지 않는다.
- INSERT RETURNING은 JdbcTemplate으로 실행한다. Spring의 JpaTransactionManager가 같은 DataSource의 JDBC 연결을 해당 트랜잭션에 연결하므로 취소 JPA와 동일한 원자성 정책을 사용한다. 실패 후 행 롤백·트랜잭션 ID 변경을 실제 DB 테스트로 검증한다.
- 제약 대기 후 미래 시작을 다시 검사하고, 기한을 지났으면 방금 INSERT한 행까지 롤백한다.
- JDBC 드라이버의 SQLSTATE와 제약 이름을 함께 읽기 위해 PostgreSQL JDBC 의존성을 컴파일 범위로 올리고 분류 코드를 한 곳에 격리한다. 모든 무결성 오류를 409로 처리하지 않는다.
- 40P01의 새 트랜잭션 재시도는 제한적 복구 정책이다. 소진 시 503이며 높은 처리량이나 모든 상황의 성공을 보장하지 않는다.
- 과거 실험은 DB 수준 비교이고 이번 전환의 성능 보장은 아니다. 실제 성능 수치는 이번에 새로 측정하지 않는다.

근거: [PostgreSQL 배타 제약](https://www.postgresql.org/docs/17/rangetypes.html#RANGETYPES-CONSTRAINT), [배타 검사 대기·교착 구현 설명](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/executor/execIndexing.c#L27-L44).

### 오류 분류와 실제 트랜잭션 복구

- 단위 테스트는 명명된 해당 제약의 23P01과 다른 제약 이름·23503·23505·40001·55P03·57014를 구분한다. 원인/SQLException.nextException의 40P01, 재시도 후 중복, 3회 소진, 취소 재시도, 인터럽트 보존을 검증했다.
- 실제 교착 테스트는 테스트 전용 AFTER INSERT 트리거와 별도 JDBC 트랜잭션이 advisory lock 90101·90102를 반대 순서로 획득해 두 트랜잭션의 순환 대기를 만든다. PostgreSQL 서버의 deadlock detected·advisory lock 대기 관계 로그를 확인하고, 첫 쓰기 롤백·서로 다른 transaction ID·시도 2회·최종 예약 한 건·API 201을 확인했다. 배타 인덱스 내부 교착을 고부하로 재현한 테스트는 아니다.
- 별도 테스트 트리거의 40P01 주입은 실제 PostgreSQL 오류·롤백 경로에서 최초 포함 3회 제한과 503을 검증한다. 생성 소진 후 행 0건, 취소 소진 후 CONFIRMED·cancelled_at NULL 유지, 트리거 제거 후 정상 요청 복구를 확인했다. 주입 테스트와 위 실제 교착 테스트를 구분한다.
- DO NOTHING의 빈 결과는 409로 처리한다. 다른 UNIQUE 위반은 500으로 남겨 예약 중복으로 오인하지 않았다. 원인 SQLSTATE가 40P01일 때만 재시도한다.
- 기존 생성·취소 경합 3회, 동일 예약 동시 취소 8개, 예약 행 잠금 대기 후 시작 시각 경과·기존 취소 시각 보존을 검증했다. 공간의 FOR NO KEY UPDATE와 무관한 예약 생성·취소 완료로 공간 쓰기 잠금 제거를 확인했다.
- V3 확정·취소 이력 보존 후 V4 적용과, 기존 활성 중복이 있으면 V4가 실패해 기존 데이터·버전 3이 유지되는 경우를 검증했다.

### 실패와 수정 이력

1. 구현 전 직접 SQL 겹침 테스트는 차단되지 않아 실패했고, 공간 잠금 독립성 테스트도 시간 초과로 실패했다.
2. 단순 INSERT·최대 3회 재시도의 중간 구현은 8동시 테스트에서 201 한 건·503 일곱 건을 반환했다. 실제 40P01 반복을 확인하고 명명된 제약의 ON CONFLICT DO NOTHING RETURNING으로 바꿨다. 이후 기존 경합 계약을 통과했다.
3. 실제 교착 복구 테스트는 이미 새 transaction ID·시도 2회·API 성공을 확인했지만 pg_stat_database 누적 통계의 즉시 증가를 기다리는 검증이 5초 내 충족되지 않았다. 카운터 반영 시점에 의존하는 대신 해당 실험 구간의 서버 교착 대기 관계 로그를 직접 검증했고 개별 테스트 및 최종 전체 빌드가 통과했다.
4. JVM 클래스 공유 경고, 의도적 DB 제약·교착·시간 초과 및 실패 마이그레이션 로그는 있었으나 최종 테스트 실패는 없다.

## 보존 및 후속 과제

변경 전 백업 45개 파일은 모두 존재한다. 전환에 필요한 서비스·저장소·테스트·문서만 갱신했으며 V1~V3는 SHA-256으로 동일함을 확인했다. 공간 등록·조회와 기존 예약 입력·취소 정책을 보존했다. 문서 참조·공백 검사를 통과했고 Git index를 변경하거나 커밋·push하지 않았다.

AC10 목록·필터, 운영 마이그레이션 잠금 계획·확장 권한, 전체 HTTP 마감, 성능·다중 인스턴스 부하 검증은 후속 과제다. 이번 정확성 테스트 통과를 고충돌 성능 보장으로 일반화하지 않는다.
