# 예약 생성·취소 API

## 범위와 구현 순서

[요구사항](requirements.md)의 예약 생성·취소와 동일 공간 중복 방지를 구현한다. 예약 목록(AC10), 인증, 시간 변경, 프런트엔드는 포함하지 않는다.

1. PostgreSQL·HTTP 테스트로 생성·취소·입력·시간 경계·동시 요청의 미구현 실패를 확인한다.
2. V3 마이그레이션과 reservation 패키지, 공통 오류 매핑을 구현한다.
3. 동시성 대안을 비교하고 선택한 방식의 잠금·롤백·경계 동작을 테스트한다.
4. 전체 빌드·테스트 결과와 실패 원인을 기록한다. 커밋·push는 하지 않는다.

## API 계약과 구현 기본값

- `POST /api/reservations`: `spaceId`(양의 정수), `bookerName`(필수, 최대 100자), `startAt`, `endAt`으로 예약하고 201을 반환한다.
- `POST /api/reservations/{id}/cancel`: 시작 전 확정 예약을 취소하고 200을 반환한다. 취소 이력을 보존한다. 이미 취소된 예약이면 시작 시각과 무관하게 200을 반환하며 최초 취소 시각을 유지한다.
- 응답은 `id`, `spaceId`, `bookerName`, `startAt`, `endAt`, `status`, `createdAt`, `cancelledAt`이다. 상태는 CONFIRMED·CANCELLED다.
- 입력 시각은 오프셋을 포함한 ISO-8601 문자열이다. 같은 순간은 UTC Instant로 비교·응답한다. PostgreSQL에 맞춰 마이크로초 정밀도까지 허용하고 더 세밀한 시각은 400으로 거부한다. 지원 UTC 연도는 1~9999다.
- 시작 < 종료이며, INSERT 실행 전후 Clock으로 검사한 현재 시각보다 시작이 미래여야 한다. 제약 대기 중 시작에 도달하면 롤백한다. 구간은 `[시작, 종료)`여서 맞닿는 예약을 허용한다.
- 잘못된 입력·구간은 400, 없는 공간·예약은 404, 확정 예약의 중복 또는 시작 시각에 도달한 예약의 최초 취소는 409다. 오류 형식은 기존 code·message·fieldErrors를 따른다.

| 오류 | 상태 | code |
| --- | --- | --- |
| 필수값·길이·양수 검증 | 400 | VALIDATION_ERROR |
| JSON·ISO 시각·ID 형식 오류 | 400 | INVALID_REQUEST |
| 시간 순서·미래 시작·정밀도·지원 연도 위반 | 400 | INVALID_RESERVATION |
| 공간·예약 없음 | 404 | SPACE_NOT_FOUND / RESERVATION_NOT_FOUND |
| 확정 예약과 겹침 | 409 | RESERVATION_CONFLICT |
| 시작에 도달한 확정 예약 최초 취소 | 409 | RESERVATION_ALREADY_STARTED |
| 일시적 잠금·쿼리 시간 초과 | 503 | TEMPORARY_DATABASE_FAILURE |

요청 예시:

```json
{"spaceId":1,"bookerName":"예약자","startAt":"2030-01-01T10:00:00+09:00","endAt":"2030-01-01T11:00:00+09:00"}
```

V3는 공간 FK, 시작 < 종료, 예약자명 필수, 상태 값과 cancelled_at 정합성 제약을 추가한다. V4는 CONFIRMED 한정 배타 제약을 추가한다. 각 생성·취소 시도는 독립 트랜잭션이며 실패 시 롤백한다. 재취소는 최초 취소 시각을 유지한다.

## 동시성 대안 비교와 결정 기준

| 후보 | 보장과 비용 |
| --- | --- |
| 공간 행 비관적 잠금 + READ COMMITTED | 예약이 전혀 없는 구간도 공간 행으로 직렬화한다. JPA·일반 SQL로 구현 가능하다. 같은 공간의 겹치지 않는 요청도 대기하며 모든 변경 경로가 잠금 규약을 따라야 한다. |
| PostgreSQL tstzrange 배타 제약 | 직접 DB 쓰기까지 중복을 차단한다. btree_gist 확장과 PostgreSQL 전용 스키마·오류 처리가 필요하며 동시 충돌·교착 재현을 별도로 검증해야 한다. |
| SERIALIZABLE | 읽기·쓰기 경쟁을 감지한다. 직렬화 실패를 정상 응답으로 복구할 제한 재시도 정책이 필요하다. |

현재 구현은 **CONFIRMED 한정 배타 제약과 예약 행 취소 잠금**을 채택했다. 직접 SQL에도 무결성을 강제하며 같은 공간의 무관한 시간대를 공간 행으로 직렬화하지 않는다. 이전 공간 행 잠금 구현과 실험의 경위를 포함한 전환 판단·제한 재시도·검증 결과는 [reservation-concurrency.md](reservation-concurrency.md)를 따른다.

각 시도는 REQUIRES_NEW·READ COMMITTED다. 생성은 존재·시각 확인 → 명명된 배타 제약을 지정한 INSERT ON CONFLICT DO NOTHING RETURNING → 현재 시각 재확인 순서다. 반환 행이 없으면 중복 409로 처리한다. 취소는 예약 ID 행을 잠근 후 읽은 상태와 Clock으로 판단해 변경한다. 공간 행 잠금과 사전 중복 조회는 사용하지 않는다.

잠금은 커밋·롤백까지 유지한다. 해당 예약 배타 제약의 23P01만 중복으로 매핑한다. 40P01은 실패한 트랜잭션 종료 후 새 트랜잭션에서 최대 3회(최초 포함) 시도한다. 시도 사이 10~30ms jitter를 적용하며 소진·인터럽트·다른 일시적 시간 초과는 503이다. 각 시도는 15초 제한이고 전체 요청 전역 제한은 아니다. 배타 제약은 직접 SQL의 활성 중복도 막지만 최초 취소 시각·미래 시작 정책은 애플리케이션이 검증한다.

근거: [PostgreSQL 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html), [배타 제약](https://www.postgresql.org/docs/17/ddl-constraints.html). 아래 88개 결과는 전환 전 공간 행 잠금 구현 당시의 기록이며, 현재 전환 결과는 별도 문서에 기록한다.

## 초기 공간 행 잠금 구현의 검증 결과 (2026-10-28)

`backend/`에서 실행:

```powershell
.\gradlew.bat clean build --no-daemon
```

최종 결과는 **BUILD SUCCESSFUL**, 약 57초. 총 88개 테스트(예약 40, 공간 45, 환경·마이그레이션 3)가 통과했고 실패·오류·건너뜀은 모두 0이다. PostgreSQL 17.11 Testcontainers를 사용하며 H2로 대체하지 않았다. 테스트 서버와 컨테이너는 종료·정리되었고 Compose 개발 DB는 사용하지 않았다.

- 순차 통합: 생성·UTC 변환·부분 겹침·양방향 포함·동일 구간 거부, 양끝 맞닿음 허용, 다른 공간 허용, 취소 후 재예약, 시각과 무관한 재취소 및 최초 취소 시각 보존, 시작 시각 이후 최초 취소 거부를 확인했다.
- 입력과 DB: Clock을 고정해 현재·과거·같은 시각 경계를 검증했다. 필수값·최대 길이·숫자 타임스탬프·오프셋 없는 시각·마이크로초·DB FK 및 시간 구간 제약을 확인했다.
- 동시 생성: CountDownLatch로 독립 HTTP 요청 8개를 함께 출발시키는 테스트를 3회 반복했다. 매번 201 한 건·409 일곱 건이고 모든 요청 완료 후 DB 확정 예약은 한 건이었다. 각 HTTP 요청이 별도 서비스 트랜잭션을 사용하며 테스트 전체를 하나의 트랜잭션으로 감싸지 않았다.
- 동시 변경: 같은 예약의 동시 취소 8개는 모두 200이었다. 생성·취소 경쟁은 3회 반복해 최초 취소 성공과 최종 확정 예약 최대 한 건을 확인했다. 다른 공간 및 같은 공간의 겹치지 않는 동시 생성은 모두 성공했다.
- 실패 복구: 별도 JDBC 트랜잭션으로 공간 행을 잠그고 pg_stat_activity에서 실제 대기를 확인한 후 Clock을 시작 시각으로 전진시켰다. 잠금 해제 후 생성은 400이고 데이터는 없었다. 별도 잠금 시간 초과 테스트는 503과 롤백을 확인한 뒤 잠금 해제 후 새 요청이 201로 성공했다.
- 마이그레이션: 빈 DB 기동, V1→V2, 기존 공간 데이터가 있는 V2→V3 업그레이드를 검증했다. V1·V2 파일은 수정하지 않았다.
- 문서 참조와 `git diff --check`, 신규 파일 공백 검사를 통과했다. 커밋·push는 수행하지 않았다.

### 실패와 수정

1. 테스트를 먼저 작성한 상태에서 32개가 reservations 테이블 부재로 실패했다. V3와 API·잠금 구현 후 기본 빌드가 성공했다.
2. 추가한 숫자 시각 입력 테스트 2개는 Jackson의 기본 OffsetDateTime 역직렬화가 숫자를 허용해 실패했다. 예약 시각 두 필드에만 ISO 문자열 역직렬화를 적용하고 재검증했다.
3. 생성·취소 경쟁 3회는 실제 결과가 정상적인 `[200,201]` 또는 `[200,409]`였지만 테스트의 containsOnly 검증식이 세 상태 모두를 요구해 실패했다. 허용 상태 검사로 테스트를 바로잡았다. 최종 전체 빌드에서 모두 통과했다.
4. 테스트 JVM 클래스 공유 경고와 의도적 DB 잠금 시간 초과 로그는 있었으나 최종 테스트 실패는 없었다.

## 남은 작업

예약 목록·필터 계약과 구현(AC10), 인증·소유자 권한, 배포는 별도 작업이다. CI 구성은 main에서 반영했으며 실행 절차는 [backend-setup.md](backend-setup.md)를 따른다. 예약 API를 포함한 통합 상태의 원격 CI 실행 결과는 아직 확인하지 않았다. AC10은 사용자 확인에 따라 이번에도 미구현·미검증이다. 성능·실행 계획·다중 인스턴스 부하는 이번 전환 검증에 포함하지 않는다. V4 적용 전 활성 중복 데이터와 확장 설치 권한을 확인해야 한다.
